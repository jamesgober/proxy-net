# proxy-net v0.5.0 - Feature complete

**Every feature planned for 1.0 is in.** v0.5.0 adds TLS and the PROXY protocol toward upstreams, the WebSocket bridge, and live changes: reload the configuration, replace a pool's endpoints, or drain one endpoint while the proxy runs, with discovery behind an address allowlist. Endpoints that come back, or that a change adds, ramp up instead of taking a full share at once.

```rust
let running = proxy_net::proxy("0.0.0.0:8080", ["10.0.0.1:80"])?;
let handle = running.handle();
handle.set_endpoints("default", &[
    proxy_net::Endpoint::parse("10.0.0.1:80")?,
    proxy_net::Endpoint::parse("10.0.0.2:80")?,
])?;
handle.drain_endpoint("default", proxy_net::Endpoint::parse("10.0.0.1:80")?.addr());
```

## What is proxy-net?

A reverse proxy and load balancer for services on serve-net. Requests and responses are parsed strictly and written again, never passed through as raw bytes; client-sent forwarding headers are always removed and rebuilt from the real client; paths that a proxy and an origin could read differently are refused by default.

## What's in 0.5.0

- **Live changes.**
  - `reload` checks a new configuration, builds its running state beside the current one, and swaps it in. On an error nothing changes.
  - `set_endpoints` replaces one pool's endpoints; `drain_endpoint` takes one out of rotation while its exchanges finish, and it stays drained across reloads.
  - An endpoint present before and after keeps its health, its warm connections, and its ramp, so a reload cannot re-admit an ejected endpoint.
  - A request whose head arrived before a change is routed and checked again under the new configuration, so one request is never judged by two.
- **Discovery.** `StaticDiscovery`, `DnsDiscovery`, or your own `Discovery`, refreshed from the health checker thread.
  - `discovery_allow` takes CIDR ranges; only addresses inside them are kept.
  - Without ranges, discovered loopback, link-local (where cloud metadata services live), unspecified, multicast, and broadcast addresses are refused.
  - A source that fails, or gives nothing usable, leaves the pool as it was and is reported.
- **TLS to upstreams** (feature `tls`). Certificates are always verified, against the Mozilla roots or only the roots you give; a server name and a client certificate are optional. A pooled TLS connection is reused only when nothing is waiting on it.
- **The PROXY protocol to upstreams.** Version 1, or version 2 with the authority and a CRC32C. Health checks send `LOCAL`. A connection that carries a header names one client, so it is never reused.
- **The WebSocket bridge** (feature `ws`). serve-net terminates the client's WebSocket and ws-net opens a new one to the upstream. Every message is parsed and written again. The client gets its 101 only after the upstream's genuine 101 with the right accept key, so a fake upgrade opens no tunnel.
- **Slow start.** `Pool::slow_start(ramp)`: a returning or newly added endpoint takes a tenth of its turns at first and all of them at the end of the ramp. It adds no lock to the pick path.
- **Request ids.** `ProxyBuilder::request_id("x-request-id")` keeps a caller's id when it is a plain token of at most 64 bytes, and writes a new 32-character one otherwise.
- **Append mode.** With `Forwarded::append_trusted`, the entries your trusted proxies added stay and this hop is added; anything a client wrote before them is removed.
- **Large-response reports.** Each route keeps a moving mean of its response sizes, and a response far above it goes to `Observer::response_outlier`. It is reported, never blocked.
- **`docs/ARCHITECTURE.md`**: the layers, the threads, one request end to end, and how live changes swap the running state.

## Changed

- `ProxyHandle::balancer` is replaced by `ProxyHandle::is_eligible`, and `Proxy::config` returns an owned `Config`. The running state can now be swapped, so a reference into it cannot be handed out.
- Slow start is set per pool (`Pool::slow_start`), not per endpoint as first planned.
- An address range with bits set past its prefix, such as `10.1.0.0/8`, is refused as a likely typo.

## Tested

- Socket tests for reload, endpoint replacement, draining, discovery refreshes, the allowlist, PROXY v1 and v2 headers, request ids, and slow start carried across reloads.
- WebSocket: ambiguous paths refused on upgrade routes too, messages both ways through the bridge, the upstream's subprotocol passed on, and an upstream that answers 200 or a 101 with the wrong accept key getting no tunnel.
- TLS: settings that cannot load refuse the build, and a plain upstream behind a TLS pool gets no request in the clear.
- Unit tests for append mode, the request-id rule, ramps, and address ranges.
- Eight fuzz targets, including a new one for append mode and request ids.
- Linux, macOS, and Windows, on stable and 1.85.

## Known gaps

- **`wss` upstreams are not bridged yet.** The bridge reads and writes the upstream from two threads, and a TLS stream cannot be split; a WebSocket route to a TLS pool answers 502. This comes with the reactor path in 0.6.
- **Upstream closes reach the client late.** serve-net cannot close a client's WebSocket from outside a callback, so an upstream close reaches the client at its next message or at the tunnel idle timeout.
- **No certificate pinning by key.** tls-net has no SPKI pins yet; pin by trusting only a private CA.
- **Blocking workers only**, and the response limits of serve-net 0.8 (no 103 or trailers, at most 64 response fields, known lengths sent chunked), as in 0.4.

## Who should use it

Anyone who wants a proxy or load balancer in front of HTTP/1.1 servers, including over TLS, for WebSocket applications, or behind a load balancer that speaks the PROXY protocol. It is pre-1.0: benchmarks, long fuzz campaigns, and soak tests come next.

## What's next

`0.6.0`: benchmarks against other proxies and the optimisation they point to, the reactor path once serve-net can park a streamed reply, and `wss` upstreams through the bridge.
