# proxy-net v0.6.0 - Optimisation

**Measured against nginx, HAProxy, and Envoy, and faster where the numbers pointed.** v0.6.0 bridges WebSockets to TLS upstreams, cuts the allocations of a proxied request from 42 to 10, takes system calls out of the connection pool's lock, and indexes routes by host. `docs/PERFORMANCE.md` has every number and how it was measured.

```rust
// Behind a load balancer: every client arrives from its few addresses.
let proxy = proxy_net::ProxyBuilder::new()
    .pool("app", proxy_net::Pool::new(["10.0.0.1:80"]))
    .build()?;
let running = proxy.serve_with("0.0.0.0:8080", proxy_net::Inbound::new().max_per_source(224))?;
```

## What is proxy-net?

A reverse proxy and load balancer for services on serve-net. Requests and responses are parsed strictly and written again, never passed through as raw bytes; client-sent forwarding headers are always removed and rebuilt from the real client; paths that a proxy and an origin could read differently are refused by default.

## What's in 0.6.0

- **`wss` upstreams.** A WebSocket route to a pool with TLS is bridged. The certificate is verified before the upgrade is sent, so an upstream that fails the handshake never sees one. The bridge's two threads share the TLS session under one lock, so records leave in the order they were sealed.
- **Against other proxies**, on a 4-CPU Linux runner with the load, the proxy, and the origin sharing it:

  | | 1 connection | 16 connections | 64 connections |
  |---|---:|---:|---:|
  | proxy-net | 19,657/s, 48 us p50 | 107,750/s | 96,336/s |
  | nginx | 19,689/s, 45 us p50 | 164,405/s | 166,517/s |
  | HAProxy | 24,390/s, 25 us p50 | 144,205/s | 147,465/s |
  | Envoy | 15,123/s, 65 us p50 | 56,298/s | 62,274/s |

  Level with nginx on one connection; about two thirds of nginx under concurrency, where one blocking thread per connection costs it, and ahead of Envoy throughout.
- **10 allocations per request instead of 42.** Each worker keeps a few buffers between exchanges, and head rewriting reads the client's fields in place. `tests/alloc.rs` counts them and fails above 12.
- **A connection pool without system calls under its lock.** Every worker forwarding to one endpoint used to queue behind the others' socket probes: about 60,000 requests per second on Linux at any concurrency. Now 409,000 at 64 connections.
- **Routes indexed by host.** A match among 32 routes takes 39 ns instead of 86 ns, still with no allocation.
- **`Proxy::serve_with` and `Inbound`.** Workers, the per-source connection cap, and a connection cap. The per-source cap stays 16 by default as a defence on an open listener; behind a load balancer, raise it, or connections above the 16th from one address are closed as they arrive.
- **Two decisions, with numbers.** permessage-deflate stays off through the bridge: recompressing would cost about 7 us per 1 KiB message and 0.7 MB per tunnel, and passing compressed messages through would carry what the proxy cannot check. A gradient concurrency limit was tried in a simulation: no capacity lost and p99 a third to two thirds lower under overload; it is kept as an experiment until a socket-level sweep agrees.

## Changed

- `RequestParts::fields` is a `FieldList`.
- `Finished` borrows: `Finished<'a>` with `pool: &str` and `endpoint: Option<&EndpointAddr>`. An observer that keeps them copies what it keeps.
- With the `tls` feature, a pool's TLS settings are loaded even when a custom connector is set.

## Tested

- `wss`: messages both ways, one larger than a TLS record; an upstream pushing to a silent client; an untrusted certificate and a wrong name getting no upgrade; 200 messages in each direction at once (run by hand, see the known gaps).
- Allocations per proxied request, and none in route matching; route matching against a reference matcher on 20,000 generated requests, and a test for the host index.
- The adaptive-limit simulation across five loads and a slowing endpoint.
- Eight fuzz targets; Linux, macOS, and Windows on stable and 1.85.

## Known gaps

- **serve-net 0.8** can hold messages queued for a WebSocket client until its next ping when the client is sending at the same time: most runs on Windows, often on a loaded Linux machine. Every message reaches serve-net without an error; the fix belongs there. The two pipelined bridge tests are ignored and run by hand.
- **Blocking workers only.** The reactor path waits on serve-net and net-io; it is the change that closes the gap with nginx under concurrency.
- **Memory per active exchange** is not measured yet; it comes with the soak tests.
